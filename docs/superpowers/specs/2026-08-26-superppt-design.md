# SuperPPT 产品与架构设计

- 初始日期：2026-08-26
- 最近修订：2026-08-30
- 状态：用户已确认；本次确定本地完整 PPT 直链、目标页页内可编辑和保存即采纳架构
- 对外名称：SuperPPT
- 内部插件及 Skill 标识：`superppt`
- 仓库：独立 `SuperPPT` 仓库

## 1. 产品定义

SuperPPT 是一个面向具有本地文件访问能力的 Agent 客户端的编排型插件。用户可以通过主题描述、粘贴长文本或导入 Markdown 文件表达要制作的内容；插件把内容逐步拆解成演示稿大纲和逐页画面描述，在五个普通确认门逐步获得用户确认后，使用高细节文生图生成整套 16:9 幻灯片，并交付 PPTX 和项目过程文件。

整套演示稿默认采用高保真图片页。用户需要修改某一页时，SuperPPT 始终从当前完整 PPTX 创建一份完整候选修订，只在这份完整文件内激活目标页的可编辑能力。用户从本地 PPT 链接在 WPS 或 PowerPoint 中打开整套 PPT，可以在全套上下文中手动编辑已激活的页面。用户回复“已保存”后，这份完整 PPTX 的当前字节直接成为新的权威修订；SuperPPT 不再重渲染、拆页、替换页、重组或二次改写用户保存的文件。

SuperPPT 不实现 PPT 预览器，也不生成 PDF、montage 或逐页图片用于 Review。每个待查看或待编辑对象都是一份完整、本地、可写的 PPTX；SuperPPT 绑定其修订 ID、绝对路径和 SHA-256，然后直接向用户提供 PPT 文件链接。WPS 或 PowerPoint 是唯一的预览和手动编辑界面。

SuperPPT 不复制两个底层能力的实现：

- `ai-image-to-ppt`：负责具体模型调用、生图、视觉检查和生成侧重试。
- `image-to-editable-pptx`：负责把指定的 1280×720 PNG 重构为清理后的背景、可编辑文字和可靠图标层。

SuperPPT 管理内容规划、风格系统、提示词编译、确认门、项目状态、版本依赖、局部重算、整套组装和最终验收。

## 2. V1 范围

### 2.1 支持的输入

- 自然语言主题或需求描述。
- 直接粘贴的长文本。
- Markdown 文件。

导入时必须保留原始输入，生成统一源稿和项目简报。V1 不解析 DOCX、PDF 或已有 PPTX；这些格式属于后续版本。

### 2.2 支持的输出

- `<项目名>.pptx`
- 当前完整 PPTX 的本地修订记录和确认记录
- 原始源稿、项目简报、整套大纲和逐页描述
- 锁定后的风格配方及引用的参考图信息
- `项目状态.md`
- `验收清单.json`

V1 不生成 PDF、逐页图片或 montage 作为 Review 产物。用户如需这些格式，可在 WPS 或 PowerPoint 中从已交付的 PPTX 导出，不进入 SuperPPT 主链路。

### 2.3 V1 非目标

- 不把整套演示稿自动转换成全可编辑页面。
- 不承诺复杂插画、纹理、面板和任意背景对象均可编辑。
- 不提供独立 Web 管理后台、云端文件回传、任务队列或多人协作界面。
- 不实现内嵌 PPTX 预览器、逐页图片降级或通用 PPTX 视觉渲染器。
- 不在 SuperPPT 中锁死 Gemini、豆包、`gpt-image-2` 或其他具体模型。
- 不复制或分叉两个底层 Skill 的代码。

## 3. 已确认的关键产品选择

1. 使用独立 SuperPPT 仓库，保留两个底层 Skill 独立演进。
2. 整套默认先生成高保真图片式 PPT，只有用户指定修改的页面才进入可编辑重构路径。
3. 五个普通人工确认门依次为：整套大纲、逐页描述、代表性风格样页、生成授权、整套回看与交付确认。
4. 用户修改某页时，既支持 SuperPPT 在完整候选 PPT 中帮助修改，也支持用户在 WPS 或 PowerPoint 中手动编辑已激活的目标页。用户手动保存并回复“已保存”即采纳完整文件；Agent 帮改则必须在用户打开完整候选 PPT 并确认后才采纳。
5. 复杂插画或大幅改版采用重新生图；文字和可靠提取对象采用可编辑重构。
6. 风格为单选，每套演示稿只有一个主风格。
7. V1 内置 8 至 12 个高细节风格，同时支持文字描述或参考图定义本项目自有风格。
8. 模型通过独立的 `ai-image-to-ppt` Skill 接入。该 Skill 完成 `gpt-image-2` 等模型支持后，SuperPPT 通过 Skill 委托直接继承，不增加模型专属业务流程。
9. 所有已确认的上游内容仍可修改；确认只建立可恢复版本基线，不是永久锁死。
10. Review 以真实完整 PPTX 修订为权威对象；SuperPPT 只提供本地文件链接，由 WPS 或 PowerPoint 完成预览。
11. V1 只支持具有本地文件能力的 Agent 客户端，不实现云端或图片预览降级。

## 4. 总体架构

### 4.1 编排层

`superppt` Skill 是面向用户的唯一入口，负责：

- 初始化或恢复项目工作区。
- 执行依赖和环境预检。
- 标准化输入并建立项目简报。
- 生成大纲、逐页描述和提示词。
- 管理五个普通确认门，以及上游修改影响、Agent 帮改采纳和手动保存采纳等条件确认门。
- 管理风格库、样页和风格配方。
- 把文生图 job 委托给 `ai-image-to-ppt`，并调用可编辑转换适配器。
- 维护页面版本与依赖失效关系。
- 组装、检查、发布本地链接和交付整套文件。

### 4.2 内容规划器

内容规划器把统一源稿转换成：

- 演示目标、受众、场景、语言、期望页数和内容约束。
- 具有叙事顺序的整套大纲。
- 每页稳定 ID、页面角色、核心观点、标题、必要文字、画面主体、信息结构和讲解目的。
- 源稿到页面的可追溯引用，避免大纲压缩时遗漏关键内容。

### 4.3 视觉导演与提示词编译器

提示词编译器不是简单拼接一段 Style 文本。它先生成结构化视觉导演稿，再映射到具体模型适配器。

每页视觉导演稿至少包括：

1. 页面目的与核心观点。
2. 页面类型和视觉主次。
3. 必须出现的场景、人物、物体、图形或关系。
4. 图文关系、阅读顺序和信息区域。
5. 构图、景别和前中后景层次。
6. 色彩、材质、纹理、光影和媒介。
7. 用于丰富画面的微小叙事元素。
8. 必须准确出现的简短文字和数量约束。
9. 风格一致性键、禁用项和负面提示词。
10. 模型输出前的自检要求。

“细节丰富”必须服从信息层级。每页仍需一个明确主视觉和清晰阅读顺序，不能把元素数量本身当作质量目标。图片内文字保持精简，复杂观点优先通过图像关系和结构表达。

### 4.4 `ai-image-to-ppt` Skill 委托层

SuperPPT 不实现文生图 Provider，也不复制宿主能力发现、模型选择、降级路由、图片导入或生成侧重试。这些能力全部由 `ai-image-to-ppt` Skill 拥有。

SuperPPT 只做 Skill 级委托：

1. 根据已确认的逐页描述和风格编译一份不可变的 `ImageGenerationJob`；job 显式绑定完整 Style Lock，不只传递风格名称。
2. 当前 Agent 加载并遵循 `ai-image-to-ppt` Skill，以一份 job 作为一个串行批次执行。
3. `ai-image-to-ppt` 负责宿主/API 候选、粘性路由、生图、宿主产物导入、raw/master 保留、16:9 规范化和安全失败分类。
4. SuperPPT 接收 `ai-image-to-ppt` 现有 `GenerationResult` 和 `SerialStickyRouter.report()` 所表达的结果，形成 `ImageGenerationResult`，再对 job、revision、提示词哈希和图片产物做本地验证。

这是一个跨 Skill 的任务/结果契约，不是第二套生成适配器。SuperPPT 不指定 `gpt-image-2`、Gemini 或豆包等模型分支；项目状态只记录依赖 Skill 身份、实际 provider/channel、提示词哈希和产物哈希。

依赖发现必须面向 Codex Skill 目录，不假设用户存在某个兄弟 Git 仓库或固定绝对路径。运行时脚本一律相对已解析的 `ai-image-to-ppt` Skill 根目录定位。

### 4.5 可编辑转换适配层

指定页进入可编辑路径前，必须从当前高保真页面产物生成精确的 1280×720 PNG。转换适配层调用 `image-to-editable-pptx`，消费其版本化输出：

- OCR 和视觉分析结果。
- 清理后的背景。
- 可编辑文字的位置与样式。
- 通过安全门的透明图标资源。
- 可编辑重构 manifest 和运行 ledger。

SuperPPT 不把整页位图误报为可编辑，也不假设被转换器保留在背景中的元素可以直接修改。

### 4.6 整套组装器

初次生成时，组装器根据当前页面清单生成结构完整的 PPTX：

- `image` 页面：放置一张覆盖整页的高保真图片。
- `editable` 页面：放置清理背景、真正的文本框和可靠图标层。

页面顺序、尺寸、模式、版本和产物来源由机器清单控制。修改循环开始后，组装器不再从单页产物重建整套 PPT。每次修改都先从当前权威 PPTX 创建完整候选修订，再在用户打开之前对指定页执行一次页内转换或 Agent 修改。未指定页在这个候选生成阶段必须保持不变。

`image-to-editable-pptx` 可以在内部生成单页中间产物，但 SuperPPT 必须在用户打开文件前将该页写入完整候选 PPTX。单页中间产物不得成为用户链接、Review 对象或最终交付物。

用户手动保存完整候选 PPTX 后，组装器和页面操作层都必须停止写入。采纳只能验证文件存在、结构有效和编辑器已释放写锁，然后把当前修订指针切换到该原文件；不得再复制、重渲染、拆页、替换页或重组。

若后续由 Agent 修改一个已经被用户手动保存过的可编辑页，Agent 必须在新的完整候选副本中直接读取并定位当前 PPTX 的真实页面对象。历史转换 manifest 只能作为对象身份提示，不得用来重建或覆盖用户已保存的当前页面。目标对象无法可靠定位时，必须说明限制并转入重新设计或用户手动编辑，不得用旧 manifest 静默回退。

### 4.7 本地完整文件修订

SuperPPT 只发布本地完整 PPTX 修订：

```json
{
  "kind": "local-pptx-revision",
  "revisionId": "<immutable-revision-id>",
  "absolutePath": "<owned-local-pptx-path>",
  "sha256": "<64-hex>",
  "state": "candidate|current|superseded",
  "editableSlideIds": ["<stable-slide-id>"]
}
```

创建候选修订时先写新的完整文件，不覆盖上一修订。对用户只输出该完整 PPTX 的本地可点击链接，不输出单页 PPT、预览图、PDF 或 montage。用户的修改请求串行处理；外部编辑器占用候选文件时，Agent 不得同时写入。

手动路径以用户回复“已保存”作为采纳指令，完成最低限度只读校验后直接切换当前修订指针。Agent 帮改路径则先提供候选完整 PPTX 链接，只有用户明确“确认”才切换指针。旧修订保留，“恢复上一版”只移动指针，不改写任何 PPTX。

## 5. 项目工作区

```text
<项目名>/
  source/
    original.md
  brief.md
  outline.md
  slides/
    <stable-slide-id>/
      spec.md
      visual-director.json
      prompt.json
  style/
    selection.json
    recipe.json
    references/
    sample/
  images/
  editable/
    internal-page-artifacts/
  output/
    revisions/
    candidates/
  failed-runs/
  项目状态.md
  superppt.json
  验收清单.json
```

`项目状态.md` 面向用户，说明当前阶段、最近确认、待处理失败页和可执行的下一步。`superppt.json` 是机器可读权威状态，记录版本、依赖、页面清单、确认门、失效原因和产物哈希。

原始导入内容只读保留。后续标准化和规划结果不得覆盖源文件。

## 6. 用户流程与确认门

### 6.0 对话式编排契约

SuperPPT 必须以引导对话推进项目，不得从导入内容开始静默执行到最终交付。每个阶段都要：

1. 展示系统对当前内容的简明理解和推荐。
2. 只追问对当前 PPT 实际有影响的缺失信息，一次聚焦一个决策。
3. 提出与当前内容相关的具体问题，不能只问笼统的“是否确认”。
4. 明确告诉用户可以修改当前结果，也可以返回修改任何已确认的上游阶段。
5. 只在当前门禁获得用户明确授权后进入下一阶段。

对话采用“阶段式引导”，不要求用户逐页批准每一次已授权的批量生成。但是，系统不得跳过内容大纲、逐页描述、风格样例、生成授权和整套回看五个普通确认门。

### 阶段 0：环境预检

只读检查两个底层 Skill、最低兼容版本、所需脚本、运行时和输出位置安全性。具体模型能力发现和凭证可用性由 `ai-image-to-ppt` 在获准执行的 job 内处理；SuperPPT 不读取、打印或写入密钥。

### 阶段 1：内容接收

接收描述、长文本或 Markdown，保存原始输入并生成 `brief.md`。简报包含用途、受众、场景、语言、建议页数、必须覆盖内容和限制。系统必须先展示已理解内容，再逐项追问真正缺失的信息；不得对所有项目机械询问同一组通用问题。

### 阶段 2：整套大纲

建立叙事顺序、页面角色、页面目的和稳定页面 ID。

人工确认门 1：用户确认整套大纲。

### 阶段 3：逐页描述

为每页建立内容与画面描述，包括标题、关键文字、核心视觉、图文关系、构图和禁止项。

人工确认门 2：用户确认逐页描述。

### 阶段 4：风格与代表性样页

用户从紧凑风格库单选主风格，或使用文字和参考图定义自有风格。系统优先选择同时含有标题、正文、关系图和视觉主体的内容页作为代表页；不默认使用封面。用户可以改选任意样页。

生成样页前，系统必须显示选定风格、代表页、`ai-image-to-ppt` 依赖身份及其路由策略、一次生图调用、对外调用和输出位置，并获得用户明确的“生成这张样页”授权。实际 Provider/channel 在依赖执行后记录，不在执行前由 SuperPPT 预测。该单次授权绑定当前 revision 和样页请求，不可用于后续整套批量生成。

人工确认门 3：用户确认风格样页。

### 阶段 5：批量生成

先显示冻结后的风格配方、`ai-image-to-ppt` 依赖身份及其路由策略、页数、调用次数上限、是否有对外调用和输出位置。实际 Provider/channel 由依赖执行结果记录。

人工确认门 4：用户明确授权开始生成。授权必须绑定当前 revision 和上述调用计划；任一上游修改都使它失效。

授权后串行生成全部页面。每页独立记录状态；质量不合格时，SuperPPT 在同一 approved Style Lock 下发布新的 page-regeneration job，且只能使用剩余已授权调用或获得追加授权。已授权批次不需要用户逐页点击确认。

### 阶段 6：组装、整套检查与 Review

先在项目所有的候选 staging 中组装 PPTX，检查页面数量、顺序、比例、裁切、内容覆盖、风格一致性和文件可打开性，随后发布当前完整候选 PPTX 的本地文件链接。系统明确引导用户在 WPS 或 PowerPoint 中打开这份真实完整 PPTX 回看，同时给出结构检查结果和待处理页面。SuperPPT 不生成内嵌预览、PDF、montage 或逐页图片，也不得直接宣布交付完成。

人工确认门 5：用户在“修改某页”、“返回修改大纲/逐页描述/风格”和“确认交付”中做出明确选择。只有“确认交付”才能将候选 staging 提升为正式 output revision。

### 阶段 7：改单页循环

接收自然语言修改要求，先将页码或标题解析为稳定页面 ID，再在当前完整 PPTX 的候选副本上选择直接编辑、转为可编辑后修改，或按 approved Style Lock 重新生成目标页。无论底层是否使用单页中间产物，用户只会收到目标页已可编辑或已修改的完整候选 PPTX 链接。

用户手动路径为“打开完整候选 PPT -> 在全套中编辑目标页 -> 保存 -> 回复已保存 -> 只读校验 -> 直接采纳该完整文件”。Agent 帮改路径为“Agent 修改完整候选 PPT -> 提供完整链接 -> 用户在 PPT 编辑器中回看 -> 确认后采纳”。采纳仅切换当前修订指针，不再导入单页或组装新 PPT。修改循环可串行执行多次。

### 阶段 8：最终交付

只在整套回看门禁指向当前 revision 且用户已选择“确认交付”后，输出当前完整 PPTX 的本地链接、确认记录、过程文件、项目状态和验收清单。SuperPPT 不附加 PDF、逐页图片或 montage。

除五个普通确认门、上游修改的影响确认和改单页 Review 确认外，机器可完成的阶段应自行继续，不增加无必要的等待点。

## 7. 风格系统

### 7.1 选择界面

- 使用紧凑的 3×3 或 4×3 高细节 16:9 缩略图网格。
- 每个缩略图只显示短名称，点击后才展开大图、适用场景和说明。
- 风格只能单选。
- V1 内置约 10 个高细节方向，至少覆盖水墨未来、科学图鉴、三维微缩、电影编辑、先锋瑞士和电影科技等已认可方向。

### 7.2 风格配方

每个风格配方包含：

- 色彩系统。
- 材质与纹理。
- 光影与氛围。
- 插画、摄影或三维媒介。
- 字体气质和文字安全区。
- 信息密度和构图原则。
- 图形与装饰语言。
- 固定元素、禁用元素和负面提示词。
- 适用页面类型及页面类型变体。

同一套演示稿共享风格配方，但封面、章节页、流程页、对比页、数据页和总结页采用不同构图策略，避免整套像重复模板。

### 7.3 Style Lock 与生图委托

用户选定风格和代表页后，SuperPPT 先将风格配方、页面类型变体、禁用项和参考素材哈希冻结为 provisional Style Lock，用于生成代表性样页。用户确认样页后，SuperPPT 将样页路径和哈希并入 approved Style Lock。后续整套、重试和单页重生的每个 `ImageGenerationJob` 都自动绑定这一 approved 版本，不要求用户重复选择或重述风格。

SuperPPT 提示词编译器必须把完整配方和当前页面类型变体写入规范化 Style Lock 区块，并为配方、样页和最终提示词分别记录 SHA-256。`ai-image-to-ppt` 应把这视为用户已选定的自定义艺术方向，不得再叠加其默认米白教科书风或其他冲突的默认 Style 块。

Provider/channel 切换只能改变调用通道，不得改写当次 job 的最终提示词文本。若质量检查需要定向修正提示词，SuperPPT 必须在同一 Style Lock 下发布新的 page-regeneration job 和新提示词哈希，而不是让依赖在不可见的内部改写。任何新提示词都不得修改 Style Lock 的色彩、材质、光影、媒介、字体气质、构图原则、详情语言和禁用项语义。若依赖无法保留该风格，应返回结构化失败，不应静默降级为默认风格。

### 7.4 自定义风格

用户可以输入风格描述或提供参考图。系统据此生成本项目风格配方和代表页；用户确认后，将配方、参考图哈希、样页、模型、参数和提示词哈希保存为当前风格版本。

## 8. 可回溯版本与局部重算

所有确认结果都是可撤销的版本基线。用户可以在任何后续阶段修改 `brief.md`、大纲、逐页描述或主风格。

修改流程：

1. 解析用户要修改的上游对象。
2. 计算受影响的下游页面和整套产物。
3. 向用户展示影响范围。
4. 用户确认后创建新修订，不覆盖旧版本。
5. 只把依赖于旧版本的产物标记为失效。
6. 从最早受影响阶段重新确认或执行。
7. 保留随时回到上一确认版本的能力。

### 8.1 稳定页面身份

每页使用稳定 ID，页码只是当前排序。调整大纲顺序时，未改变内容和风格依赖的页面可以复用图片；只需更新顺序并重组整套文件。

### 8.2 失效规则

| 修改对象 | 失效范围 |
|---|---|
| 某页文字或画面描述 | 该页提示词、图片、可编辑衍生物、整套导出 |
| 页面顺序 | 页面清单顺序和整套导出；未变页面可复用 |
| 新增或删除页面 | 相关大纲、逐页描述、目标页面和整套导出 |
| 主风格或风格配方 | 全部页面图片、可编辑衍生物和整套导出 |
| 受众、用途或核心表达目标 | 从大纲开始重新确认，影响范围由内容规划器计算 |

## 9. 单页修改路由

### 9.1 请求定位

用户可以用当前页码、标题或内容指代页面。系统把指代解析为稳定页面 ID，并保存原页和当前整套版本。

### 9.2 修改分类

- 文本修改：标题、正文、标签或数字替换。
- 可提取元素修改：可靠图标的移动、缩放或替换，以及受支持的样式变化。
- 复杂视觉修改：主插画、整体布局、背景、材质或大幅构图变化。

### 9.3 执行策略

- 文本和可靠元素：若页面仍是图片页，先调用可编辑转换；若页面已可编辑，则直接操作完整候选 PPTX 中的当前真实对象，不用历史 manifest 重建该页。用户可选择由 SuperPPT 执行受支持操作，或在 WPS/PowerPoint 中手动编辑。
- 复杂视觉：更新该页视觉导演稿和提示词，重新生图；用户仍要求后续可编辑时，再对新图片执行转换。
- 目标对象未被转换器可靠提取：不得假装修改成功，自动切换为重新生图或向用户说明真实限制。

### 9.4 完整候选文件采纳

修改开始时，SuperPPT 先复制当前权威 PPTX 为新的完整候选修订。如目标页尚不可编辑，则在用户打开文件前将转换结果写入该候选的指定页。对用户只发布这份完整 PPTX 的本地链接。

手动 Office 编辑采用“保存并回复已保存即采纳”的语义。SuperPPT 只读检查该完整文件的存在性、写锁和 PPTX 包结构，然后计算新 SHA-256 并切换当前修订指针。不得为了居中、排版、生成预览、统一样式或替换页面再执行任何文件写入。

Agent 帮改则先写完整候选 PPTX，提供链接和修改摘要，并等待用户确认。确认必须绑定当时的候选 SHA-256；若文件在确认前发生变化，旧确认失效。拒绝修改时保留现有当前版本。

## 10. 质量门与错误处理

### 10.1 生成前

- 依赖能力和版本通过预检。
- 页面清单、稳定 ID 和顺序有效。
- 大纲、逐页描述、风格样例和生成授权四个生成前门禁均指向当前上游版本。
- 批量生成前显示页数、依赖 Skill、路由策略、调用次数上限和输出位置，并获得明确授权；实际模型/Provider/channel 在执行结果中记录。

### 10.2 单页生成质量

- 输出为有效 16:9 页面。
- 标题和必须文字与逐页描述一致。
- 数量敏感元素满足明确数量约束。
- 主视觉、阅读顺序、图文关系和页面角色正确。
- 画面达到风格配方规定的材质、光影、空间和细节密度。
- 与代表性样页保持可接受的风格一致性。
- 不出现禁止元素、水印、明显乱码或无意义装饰堆叠。

OCR 和视觉检查失败时，系统针对失败项生成新的 page-regeneration job 和新提示词哈希，只重生当前页。重生次数受当前授权的总调用预算约束，不得由 Provider 降级、切换或隐藏重试绕过；预算不足时先向用户说明并获得追加授权。仍不合格时，保留失败证据和已通过页面，停止把该页标记为可交付；用户可以明确要求继续尝试。

### 10.3 原子产物

生成、转换和整套导出先写入暂存目录。全部必要产物完成并通过结构检查后，才提升为当前正式版本。失败运行进入 `failed-runs/`，不能覆盖上一个成功版本。

外部 PPT 编辑器打开完整候选修订后，该修订进入 `external-editing` 状态。在用户回复“已保存”且写锁释放之前，Agent、页面操作层和组装器都不得写入该文件。采纳开始后只允许读取、校验、计算哈希和更新项目状态。

已有输出目录只有在包含有效 SuperPPT ownership marker 时才允许由本插件替换。未标记目录、项目根、源文件、祖先目录和不安全符号链接路径必须拒绝。

### 10.4 凭证与隐私

- 只检查凭证是否存在，不打印或记录值。
- 运行记录和错误证据必须脱敏。
- 调用模型前说明将发送的页面内容或图片。
- 项目文件不能被静默发送给未选中的模型或服务。

## 11. 测试策略

### 11.1 单元测试

- 输入标准化和 Markdown 保真。
- 大纲与页面稳定 ID。
- 提示词编译器对不同页面角色的结构化输出。
- 风格配方继承和页面类型变体。
- 修改分类和路由。
- 依赖图、失效范围和版本回退。
- ownership marker、路径安全和原子提升。

### 11.2 契约测试

- `ai-image-to-ppt` 当前生成接口及后续能力声明。
- `gpt-image-2` 等模型通过适配器出现时不改变编排状态机。
- `image-to-editable-pptx` 输入尺寸、输出 manifest、背景、文字和图标资产契约。
- 组装器消费的可编辑页 artifact schema。
- 本地完整 PPTX 修订的绝对路径、哈希、可编辑页 ID 和状态契约。
- 手动保存采纳与 Agent 帮改确认的不同状态转换契约。

### 11.3 集成测试

- 使用离线 fixture 跑通输入、大纲、页面描述、风格锁定、批量生成状态、混合页面组装和导出。
- 模拟单页失败、重试、恢复和旧版本保留。
- 修改单页描述后只重做该页。
- 修改页面顺序后复用未变图片。
- 修改主风格后全部页面正确失效。
- 可编辑对象缺失时正确转为重新生图路径。
- 候选整套 PPT 只激活指定页的可编辑能力，未指定页在打开前保持不变。
- 手动保存并采纳后文件字节不发生任何二次写入，后续改页从这份完整修订继续。
- Agent 帮改未经确认时不得替换当前修订，确认后只切换指针。

### 11.4 真实验收

- 使用真实模型生成一张高细节代表页并完成 OCR、视觉和风格检查。
- 生成一套小型样例演示稿，提供完整 PPTX 本地链接，并在 WPS 或 PowerPoint 中完成整套回看。
- 从当前整套修订创建候选副本，只把一页转换为可编辑页，但用户打开的始终是完整 PPT。
- 在目标 WPS 或 PowerPoint 中打开受控 smoke 副本，临时编辑选定文字或对象，撤销后选择不保存，关闭并重新打开。
- 单独执行一次真实手动编辑、保存与采纳，验证 SuperPPT 没有再次改写用户编辑结果，并由新 PPTX 哈希建立确认。
- 验证页数、顺序、比例、字体显示、裁切、可编辑性和最终文件显示结果。

自动化测试通过不能替代真实客户端验收。

## 12. 验收标准

V1 只有同时满足以下条件才可称为完成：

1. 新建和恢复项目工作区均可用。
2. 三种输入方式均能进入统一流程。
3. 五个普通确认门按顺序工作，每步使用与当前内容相关的引导问题，并允许回改上游内容。
4. 风格库使用紧凑单选缩略图，内置风格均有真实高细节预览。
5. 代表页确认后先显示生成计划并获得授权，然后才能批量生成；失败页可定向重试和恢复。
6. 提示词编译器能生成图文并茂、层次明确、细节丰富的页面提示词。
7. 修改依赖图能够准确局部失效，并保留旧版本。
8. 简单改单页路径能产出真正可编辑的文字或可靠对象。
9. 复杂修改能切换到重新生图，不虚报可编辑能力。
10. 候选完整 PPT 只激活目标页，用户不需要打开单页 PPT，未改页在候选生成阶段保持不变。
11. 用户必须通过本地链接在 WPS 或 PowerPoint 中打开当前真实完整 PPTX，明确选择“确认交付”后，PPTX、确认记录和验收清单才提升为当前正式项目版本。
12. 运行宿主必须提供本地文件访问和可点击文件链接能力；不提供云端或图片预览降级。
13. 采纳和 Agent 确认绑定真实完整 PPTX 修订与 SHA-256，不绑定 PNG、PDF 或 montage。
14. 用户在 WPS/PowerPoint 保存并回复“已保存”后，SuperPPT 直接采纳这份完整 PPTX，不再二次修改、复制或重组。
15. Agent 帮改后提供完整候选 PPTX 链接，用户确认前不得采纳。
16. 后续改任意页都从最新采纳的完整 PPTX 继续，旧修订可恢复。
17. 真实 WPS 或 PowerPoint 验收通过。

## 13. 插件包装

SuperPPT 使用标准 Codex 插件结构：

```text
SuperPPT/
  .codex-plugin/plugin.json
  skills/superppt/
    SKILL.md
    agents/openai.yaml
    references/
    assets/styles/
  scripts/
  references/dependencies.json
  tests/
  docs/
```

插件 manifest 的展示名称为 `SuperPPT`，目录和内部 Skill ID 为 `superppt`。依赖清单是机器可读的单一来源，记录两个底层 Skill 的最低兼容版本、能力要求和发现方式。安装和验证流程只连接依赖，不复制其实现。
