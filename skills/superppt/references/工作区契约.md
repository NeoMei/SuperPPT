# 工作区契约

- 根目录必须包含 `appId: "superppt"` 的 `.superppt-project.json`。每次写入前验证规范路径、所有权、非符号链接和普通文件边界。
- `superppt.json` 是当前状态权威；页面 UUID 不因排序改变。Artifact 使用项目内相对路径、SHA-256 和 revision ID。
- 新项目先把原始输入字节保存到 `source/original.md`。Agent orchestration 依据它撰写严格 schema 的 `brief.json`、`outline.json` 和 `slides/<uuid>/spec.json`；`validate-outline` 在 specs 尚不存在时校验并发布 outline 权威视图，`validate-plan` 在 slide-specs 阶段要求全部 specs。两者都不代替语义撰写，也不能替用户确认。每次提问前从这些 artifact 摘要已知内容，只补会实质改变成品的信息。
- `style-selection --input` 必须先绑定用户单选、代表页稳定 ID 与 current project revision，进入 `style-selection`；未形成这份认证选择不得发布样页执行授权。风格确认后，`style/lock.json` 是单一 Style Lock 权威。不可变 job 中的 recipe/hash、approved sample、page spec/final prompt 和 reference snapshots 必须与锁定输入逐字节绑定；provider/channel fallback 不改写它们。
- 不得在已确认 artifact 上先写后补影响分析。上游修改先绑定不可变 impact 证据并确认，再保存 `revisions/<revision-id>/superppt.json` 快照、建立新版本、只重写 `staleSlideIds`/`restartStage` 指定的受影响规划 artifact 并重新校验。快照不可覆盖，未受影响页面保留。
- 每次 review/edit candidate 都从精确 current 完整 PPTX 复制到有所有权标记的 immutable revision 目录；用户只收到该完整文件的一个可点击链接。手动保存关闭后只稳定读取、结构校验、topology 对账和移动 pointer；Agent candidate 只在确认其精确 SHA-256 后移动 pointer。失败证据保留，前一个成功版本不变。
- current deck 的页面号只能由其 reconciled topology 解析；解析输出的 stable ID 与 `revisionId` 是同一 authority snapshot，手动 candidate 创建必须验证并使用该 revision，stale 时不得留下 session/candidate。手动保存造成的移动保留稳定 ID，删除建立 tombstone，新插入页分配 unmanaged ID 且可直接再次手工编辑。manual revision 的 `changedSlideIds` 必须来自 topology/slide XML 实际差异。每次采纳、确认、拒绝和 rollback 都恢复 `deck-review`、重绑 current、清除旧交付绑定；PPTX 字节不得被重写。
- `complete-deck-review --action confirm-delivery` 是 formal delivery 唯一入口；同一 exact current revision/absolute path/SHA 同时绑定 formal delivery、exports、acceptance 和 client metadata，不复制或重写 PPTX。旧 smoke-copy/record 路径不属于 active workspace contract。
- 项目和 npm 包中只保留 Skill contracts、全套 deck 模块、源码和必要资产；不收录用户编辑文件、临时 staging 或测试验收项目。
- Rollback 只读不可变快照，先保存当前快照再恢复目标，不删除后来产生的文件。
