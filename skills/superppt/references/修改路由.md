# 修改路由

## 上游规划修改

修改 brief、outline、页面 spec 或 style 之前，把请求映射到当前 deterministic CLI 支持的 change kind：`brief`、`outline-order`、`outline-structure` + 已有稳定 slide IDs、`slide-spec` + IDs，或 `style`。在完整演示文稿审阅中，`修改大纲` 映射为 `outline-structure` 加实际受影响的现有稳定 ID，`修改第 N 页描述` 先按当前页序解析为该页稳定 ID 再映射为 `slide-spec`，`换风格` 映射为 `style`。

1. 用 `0600` 私有 JSON 文件调用 `impact --project <root> --change <file>`；这一步只计划，不修改项目。
2. 逐项解释并展示返回的实际 `staleSlideIds`、`invalidatedOutputs`、`restartStage` 和 plan SHA，在 `revision-impact` 停止并等待精确回复 `确认`。也要明确哪些已确认内容会保留。
3. 只有收到该精确确认后，才依次调用 `approve-impact --project <root> --sha256 <plan-sha>` 和 `apply-impact --project <root>`；拒绝则保留当前版本。
4. 在新版本中只重写 impact plan 标记的规划/页面 artifact，只失效它列出的下游工作，并从 `restartStage` 对应的第一道变化门禁恢复：`outline`、`slide-specs` 或 style。若返回 style，新 current revision 的 `style-selection` 只能在 generation lease 内退役由旧 revision immutable snapshot v2 精确保存的 selection/lock/recipe；必须同时验证 current project、严格旧 revision 和子 revision `parentSnapshotDescriptorSha256`，并用可重放退役事务跨三个删除边界收敛，不能仅凭 membership/文件自洽或裸 unlink。Project rollback 在还没有 style-sample gate 时也必须从同一 descriptor-bound 快照恢复三份精确字节、`manifest.style` 和 stage；其后才可原子发布新 v2。其他受影响门禁必须逐道重新展示和确认，未受影响页面可以复用；仅排序改变可复用未变页渲染。

当请求无法由这些 deterministic CLI change kind 表达，或当前 CLI 缺少所需校验/提交路由时，立即停止，保留当前项目，报告未支持的变更和需要的产品能力。禁止静默直改 JSON、伪造 gate，或编造 `revise`/`update-outline` 等不存在的命令。

## 单页修改分类

| 用户修改目标 | 默认路由 | 可执行操作 |
|---|---|---|
| manifest 中已提取文字 | editable | `replace-text`、`set-text-style` |
| manifest 中已提取透明素材 | editable | `move-asset`、`replace-asset` |
| 只要求已提取文字/透明素材变成可编辑，不修改内容 | editable | `promote-editable` |
| manifest 中不存在的文字/对象 | regenerate | 修订 spec 和提示词后定向重生该页 |
| 主插画、人物、场景 | regenerate | 修订视觉主体后定向重生 |
| 背景、整体构图、信息布局 | regenerate | 修订构图后定向重生 |
| 当前页已是 editable | editable | 在当前 authenticated modified manifest 上继续编辑 |

背景图中保留的对象不算可编辑对象；不能把整页图片描述为可编辑。路由不确定时选 `regenerate` 并说明原因。

只对当前完整演示文稿 action 绑定的选中页执行首次 `convert-page`。如果用户明确不修改内容，只把已提取目标变成可编辑对象，可调用 `promote-editable --project <root> --slide <id> --revision <conversion-id> --element <manifest-element-id> --kind <text|asset>` 作为私有页面准备。`--element` 和 `--kind` 只证明用户所需目标已提取且类型正确；背景和未提取对象仍不可编辑。标题或对象未被提取、ID 不存在或 kind 不匹配时转为 `regenerate-slide`。已是 editable 的当前页走 `direct-edit`，不得重跑 converter。

如果用户要修改内容，用私有 edit-plan 调用 `plan-edit`/`apply-edit`；这些私有结果不直接展示。每次先用一句话说明 `direct-edit / activate-editable / regenerate-slide` 路由。用户未预选模式才问 `需要我帮你修改，还是由你手动修改？`；`帮我修改`/`你帮我修改` 等自然回答选择 Agent，`我手动修改`/`由我手动修改` 等自然回答选择手动，同时出现两类意思时拒绝并要求单选。

- 手动：先用 current revision 的 reconciled topology 把当前第 N 页解析为稳定 ID 与 `revisionId`，再把两者原样传给 `complete-deck-review --action edit-page` 与 `prepare-manual-deck --revision-id`。前者产生只能原子消费一次的 exact revision/SHA/stable slide pending binding；缺失、错页、stale 或重放必须在读取/创建 candidate/session 前失败且零残留。不得因稳定 ID 仍存在就在新 revision 上继续。成功后从精确 current 完整文件创建 candidate；WPS-native unmanaged 插入页也直接复制整套 deck 给 WPS，不要求 converter。响应只显示一个以绝对路径为 target 的完整本地 PPTX Markdown 链接、WPS/PowerPoint 是预览与编辑界面，以及全部 `reviewRequiredObjects` 标签，然后停止。`已保存` 不够；只有精确 `已保存并关闭` 才调用 `adopt-saved-deck`，adoption 只稳定读取、校验结构、对账 topology 与 slide XML，记录实际移动/插入/删除/XML 变化的 stable IDs、写入不可变元数据并移动 pointer，不在保存后写 PPTX。
- Agent：同样先以 `complete-deck-review --action edit-page` 创建一次性 exact pending binding，prepare 原子消费后从精确 current 完整字节创建 candidate，只在其内执行目标页操作；响应只显示一个完整本地 PPTX Markdown 链接、WPS/PowerPoint 界面说明、全部 `reviewRequiredObjects` 标签、简要修改说明和 SHA-256，然后停止并等待精确 `确认`。确认前 current 不变；确认必须绑定所展示 hash 后才 `confirm-agent-deck`；拒绝调用 `reject-deck-candidate`。确认/拒绝终态清除 pending binding。
- 连续：用户说“再改第 N 页”时，必须重新从最新 reconciled topology 解析 N，不沿用旧 outline 页码；新 candidate 必须从上一次采纳的精确字节创建。
- 恢复：手动采纳、Agent 确认/拒绝和 `rollback-deck` 都恢复 `deck-review` 并重绑 exact current revision/SHA，清除旧 formal delivery/exports/acceptance/client binding；`rollback-deck` 只移动 current pointer。所有 state-only 回执省略 raw path，并指向 `current-deck-link` 获取唯一完整文件链接。
